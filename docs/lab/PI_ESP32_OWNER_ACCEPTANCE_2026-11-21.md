## Read-only acceptance sequence (run locally by owner, with hardware consent)
1. Disconnect all GPIO jumper wires and external power before first USB identification. Do not power an ESP32 from both Flipper GPIO and USB. Use USB only for initial inspection.
2. Identify exact module and carrier-board markings; photograph both sides, including USB-UART chip and BOOT/EN buttons. An ESP32-WROOM module does not specify the carrier's auto-reset circuit.
3. On Pi, run `python3 --version`, `lsusb`, `ls -l /dev/serial/by-id/ 2>/dev/null || true`, and `python3 -m esptool version` (if installed). These commands do not open a serial port. Avoid publishing USB serial numbers or personal paths.
4. Record only sanitized vendor/product IDs and whether a stable `/dev/serial/by-id/` symlink exists. A device may instead appear as `/dev/ttyUSB*` or `/dev/ttyACM*`; do not assume either.
5. Verify board's **actual schematic** and 3.3 V logic before connecting Flipper/Arduino UART. Arduino Uno 5 V TX must never connect directly to ESP32 RX; use a verified level shifter. Common GND is necessary for wired UART, but do not join independent power rails.
6. For WROOM boot diagnosis: EN high for normal operation; GPIO0 held low during reset requests UART download mode on classic ESP32. GPIO2/GPIO12 are strapping pins with board-dependent restrictions; do not force levels based solely on this checklist. Record observed boot log only after owner-authorized serial inspection.
7. ESP32-S2 is a separate USB/Wi-Fi-capable device with **no Bluetooth radio**. Do not assign BLE responsibilities to it. Check native USB versus USB-UART implementation from the specific carrier schematic.
8. Only after consent, identify chip using a version-checked `esptool` **read-only chip-id** command generated by the offline planner. Its proposed command is a review artifact, not an authorization to execute; chip identification can toggle EN/BOOT via DTR/RTS. No write-flash, erase, GPIO drive, or Flipper programming in this phase.
9. Stop if 5 V exposure, unstable power, unknown pinout, serial permission errors, boot loops, or unverified board identity appear. Do not attempt automatic recovery.

If private Actions:read returns 403, mark **BLOCKED** and request owner-side permission configuration; never claim the fallback ran or publish private firmware/source/logs.
